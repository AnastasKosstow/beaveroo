Actions are the concrete steps **an Agent takes to interact with its environment**: searching the web, querying a database, sending an email, controlling a device.

For instance, a customer-service Agent might retrieve customer data, offer a support article or hand the case over to a human.

## Types of Actions

| Type of Action | Description |
|----------------|-------------|
| Information Gathering | Searching the web, querying databases or retrieving documents. |
| Tool Usage | Calling an API, running calculations and executing code. |
| Environment Interaction | Working with digital interfaces or controlling physical devices. |
| Communication | Talking to users via chat or collaborating with other Agents. |

## How is an Action written?

An LLM can only generate text. So an action is **text that describes which tool to call and with what arguments**. Depending on the format of that text, we distinguish three types of Agents:

| Type of Agent | How it writes the action |
|---------------|--------------------------|
| JSON Agent | As a JSON object with the name of the tool and its arguments. |
| Function-calling Agent | Also as JSON, but the model is fine-tuned for it and returns the call in a separate field of the response. |
| Code Agent | As a block of code that is executed by the environment. |

## The Stop and Parse approach

With a JSON Agent everything happens in three steps.

**1. Generation in an agreed format.** The model writes the action in a clear, pre-agreed format:

```text
Thought: I need to check the current weather for New York.
Action: {"action": "GetWeather", "action_input": {"location": "New York"}}
```

**2. Stopping (stop).** Right after the action, the model **must stop generating**. That hands control back to our code. If the model keeps writing, the only thing it can do is make up the result of the tool.

**3. Parsing (parse).** Our code reads the text, extracts the tool name and the arguments from it and calls the real C# method.

You will write the third step yourself at the end of this lesson.

## Function calling

Manual stopping and parsing is fragile: the model can get the format wrong or add extra text. That is why most modern models are **fine-tuned for function calling**. With them:

- we pass tools in a separate field of the request, and the model's chat template writes them into the prompt for us;
- the model returns the tool call in a **separate, structured field of the response**, not as part of the text;
- neither `stop` nor manual parsing is needed.

That is why, with these models, writing a Thought is optional: the tool call arrives directly as data. In .NET that is exactly how `Microsoft.Extensions.AI` works, which we will use to build our [first Agent](/en/ai-agents/unit-1/tutorial/).

## Code Agents

With a Code Agent the model does not write JSON, but **executable code**. Instead of asking for one tool, it can combine several calls with ordinary logic. Here is what such a model would write:

```csharp
string london = GetWeather("London");
string paris = GetWeather("Paris");

return $"London: {london}. Paris: {paris}.";
```

You do not write this code. The model generates it, and the Agent's environment runs it. A JSON Agent would do the same thing in two separate rounds of the cycle. That is the big advantage of code: **expressiveness**. Loops, conditions and intermediate variables are written naturally, and the result of one tool can be passed straight into another.

The cost is **safety**. We are running code written by an LLM, and it can be wrong or even malicious (for example after a prompt injection). Such code must run in an isolated environment: a separate process with limited rights, or a container.

In .NET, Code Agents are rare. C# code can be executed dynamically with the [Roslyn scripting API](https://github.com/dotnet/roslyn/blob/main/docs/wiki/Scripting-API-Samples.md), but libraries like `Microsoft.Extensions.AI` and Semantic Kernel rely on function calling. That is what we will use too.

## Stop and Parse in C#

Now we will write the third step of stop and parse: parsing and running one action. The first two steps are the model's job, and we don't have a model yet. So we will start from ready-made text: the same Thought and Action from the example above, written by hand.

All you need is the [.NET SDK](https://dotnet.microsoft.com/download) from [Unit 0](/en/ai-agents/unit-0/introduction/). You do not need Ollama, a model or NuGet packages.

### 1. Create the project

Open a terminal and run:

```bash
dotnet new console -n StopAndParse
cd StopAndParse
```

The first command creates a `StopAndParse` folder with a new console app, and the second enters it. Open the folder in your editor. We will work with two small files.

### 2. Write the tool and the parsing

Create a new file `Tools.cs`:

```csharp title="Tools.cs"
using System.Text.Json;

public static class Tools
{
    public static string GetWeather(string location) =>
        $"the weather in {location} is sunny with low temperatures.";

    public static string Run(string modelOutput)
    {
        int start = modelOutput.IndexOf('{');
        int end = modelOutput.LastIndexOf('}');
        string json = modelOutput[start..(end + 1)];

        JsonElement action = JsonDocument.Parse(json).RootElement;
        string tool = action.GetProperty("action").GetString()!;
        JsonElement input = action.GetProperty("action_input");

        return tool switch
        {
            "GetWeather" => GetWeather(input.GetProperty("location").GetString()!),
            _ => $"Unknown tool: {tool}",
        };
    }
}
```

The class has two methods:

- **`GetWeather`** is the tool itself. In a real app it would call a weather API, but here it just returns ready-made text.
- **`Run`** receives the text written by the model and runs the action in it. It does three things:
  1. It cuts the JSON out of the text: everything from the first `{` to the last `}`.
  2. It parses it and reads `action` (the tool name) and `action_input` (the arguments).
  3. By name it picks which C# method to call. If the model asks for a tool that does not exist, it returns the error as text.

### 3. Run one action

Open `Program.cs`, delete its contents and put the following:

```csharp title="Program.cs"
string modelOutput = """
    Thought: I need to check the current weather for New York.
    Action: {"action": "GetWeather", "action_input": {"location": "New York"}}
    """;

string observation = Tools.Run(modelOutput);

Console.WriteLine($"Observation: {observation}");

// The example ends here.
// The next step would be to send the observation back to the model.
```

In a real Agent the text in `modelOutput` comes from the model. Here we write it by hand so we can run the rest without a model.

The comment at the end marks where we stop. The next step would be to send the result back to the model, and we still don't have a model.

### 4. Start the program

In the terminal, in the `StopAndParse` folder, run:

```bash
dotnet run
```

output:

```text
Observation: the weather in New York is sunny with low temperatures.
```

Here is how the program reached that line:

1. `Tools.Run` received the two lines of text and cut out only the JSON: `{"action": "GetWeather", "action_input": {"location": "New York"}}`.
2. From the JSON it read that `action` is `GetWeather` and `location` is `New York`.
3. The `switch` recognized the name `GetWeather` and called the real C# method with the argument `New York`.
4. The method returned text, and `Program.cs` printed it as an Observation.

This is the moment when the model's text turns into a real call to a C# method.

### 5. Experiment

Try these three changes in the `modelOutput` text and after each one run `dotnet run`.

**Change the city.** Replace `New York` with `Sofia`. The Observation is now about Sofia: the argument comes from the text, not from your code.

**Ask for a tool that does not exist.** Replace `GetWeather` with `GetTime`. The program does not crash; it prints:

```text
Observation: Unknown tool: GetTime
```

That way the model would receive the error as text and could try something else.

**Break the format.** Put `GetWeather` back and delete the last `}` from the Action line. Now the program stops with a `JsonReaderException`. One missing character in the model's text is enough to break manual parsing. That is exactly why function calling exists.

---

Actions connect an Agent's reasoning to the real world. Whether they are written as JSON, a function call or code, the idea is the same: **the model describes what it wants done, and our code does it**.
