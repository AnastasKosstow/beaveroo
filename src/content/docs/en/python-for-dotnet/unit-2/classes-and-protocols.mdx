In C# almost all code lives in classes. In Python the first lesson got by without a single one: functions and the built-in collections were enough. You write a class when some data and the code that works with it have to travel together.

The syntax will look familiar from the first line. The rules underneath it are different: fields are not declared, there is no `private`, and an interface is optional.

There are seven topics. Each one starts with C# code and the same code in Python, and ends with one question. Three tasks are waiting at the end.

## A class, `__init__` and `self`

<Compare>

```csharp title="C#"
class Playlist
{
    public string Name;
    public List<string> Tracks = [];

    public Playlist(string name)
    {
        Name = name;
    }

    public void Add(string track)
    {
        Tracks.Add(track);
    }
}

var mix = new Playlist("Road trip");
mix.Add("Intro");
```

```python title="Python"
class Playlist:
    def __init__(self, name):
        self.name = name
        self.tracks = []

    def add(self, track):
        self.tracks.append(track)


mix = Playlist("Road trip")
mix.add("Intro")
```

</Compare>

There are four differences:

- **There is no `new`.** You create an object by calling the class like a function: `Playlist("Road trip")`.
- **`__init__` does the constructor's job.** Python calls it on its own, as soon as it has created the object. Names with two underscores on each side are reserved for methods the language calls for you. You will meet a few more in this lesson.
- **`self` is `this`, but you write it out.** It is the first parameter of every method, and it is the only way to reach the object's data: `self.tracks`. Without `self.` the name is a local variable, and it is gone when the method ends.
- **Fields are not declared.** An attribute appears when you assign to it, usually in `__init__`. There is no list of fields at the top of the class.

When you call `mix.add("Intro")`, Python passes `mix` in place of `self`. The call is short for `Playlist.add(mix, "Intro")`. This is where the most common mistake of the first days comes from: leave `self` out of the definition, and the method receives one argument more than it expects.

Because attributes are created by assignment, nothing stops that from happening outside the class too. `mix.owner = "Ana"` works. So does a typo: `mix.trakcs = []` creates a new attribute and leaves the real one untouched. So create every attribute in `__init__`. Their list is then in one place, and a type checker catches an assignment to a name that is not there.

## No `private`: the underscore and `@property`

<Compare>

```csharp title="C#"
class Account
{
    private int balance;

    public int Balance => balance;

    public void Deposit(int amount)
    {
        balance += amount;
    }
}
```

```python title="Python"
class Account:
    def __init__(self):
        self._balance = 0

    @property
    def balance(self):
        return self._balance

    def deposit(self, amount):
        self._balance += amount
```

</Compare>

Python has no `public`, `private`, `protected` or `internal`. Every attribute and every method can be reached from outside.

In place of `private` there is a convention: a name that starts with an underscore is internal to the class. `_balance` tells everyone who reads the code not to touch it from outside. Python does not enforce it, and `account._balance = -500` goes through without an error. Your colleagues enforce it, and so does a type checker if you turn that check on.

You will also meet names with two leading underscores, such as `__balance`. Python renames them internally to `_Account__balance`, so they do not clash with the same name in a subclass. That is still not `private`, and you rarely need it.

`@property` turns a method into a property. `account.balance` is read without parentheses, and `account.balance = 5` raises an `AttributeError`, because the property has no setter. The line with `@` above the method is called a **decorator**: a function that receives the method and replaces it with something else. It looks like a C# attribute, but an attribute only describes the method, while a decorator changes it.

When the property has to be writable too, you add a setter with the same name:

```python
class Product:
    def __init__(self, price):
        self.price = price    # runs the setter below

    @property
    def price(self):
        return self._price

    @price.setter
    def price(self, value):
        if value < 0:
            raise ValueError("price cannot be negative")
        self._price = value
```

`raise` is `throw`. The assignment in `__init__` goes through the setter as well, so `Product(-1)` raises the error too.

In C# you write `{ get; set; }` from day one, because a field that becomes a property later breaks the already compiled code that uses it. In Python that reason does not exist. A plain attribute and a property are read and written the same way, `product.price`. So start with an attribute, and turn it into a property on the day you need a check. The code that uses it does not change.

## Class attributes: `static` in Python

<Compare>

```csharp title="C#"
class Ticket
{
    public static int Issued;

    public int Number;

    public Ticket()
    {
        Issued++;
        Number = Issued;
    }
}
```

```python title="Python"
class Ticket:
    issued = 0

    def __init__(self):
        Ticket.issued += 1
        self.number = Ticket.issued
```

</Compare>

A name you assign to directly in the class body belongs to the class itself. There is one value and every object sees it, which makes it `static`. You reach it through the class name: `Ticket.issued`.

This is where the habit from C# misleads you. A line at the top of the class looks like a field declaration, but in Python it creates a shared attribute:

```python
class Playlist:
    tracks = []    # one list, shared by every playlist

    def add(self, track):
        self.tracks.append(track)


rock = Playlist()
jazz = Playlist()
rock.add("Thunderstruck")

print(jazz.tracks)   # ['Thunderstruck']
```

`self.tracks` looks for the attribute in the object first. The object has none, so Python takes the one on the class, and that one is the same for `rock` and for `jazz`. You saw the same sharing with default values in the first lesson, and the cure is the same: create the list in `__init__`, with `self.tracks = []`.

Reading through `self` reaches the class attribute, but assigning through `self` creates a new attribute on the object. That is why the counter in the example is increased with `Ticket.issued += 1`. `self.issued += 1` would have left the shared counter at zero.

### Static methods and a second constructor

A method that does not use the object is, in Python, most often a plain function in the file. You do not need a `static class Helpers` to give it a home. If you still want it inside the class, put `@staticmethod` on it and write it without `self`.

There are no overloads. A second `__init__` in the same class replaces the first. When an object can be created in several ways, you have two options. One is a parameter with a default value, as in C#: `def __init__(self, name, public=False)`. The other is a `@classmethod`:

```python
from typing import Self

class Playlist:
    def __init__(self, name: str) -> None:
        self.name = name
        self.tracks: list[str] = []

    @classmethod
    def from_text(cls, text: str) -> Self:
        parts = text.split(";")
        playlist = cls(parts[0])
        playlist.tracks = parts[1:]
        return playlist


mix = Playlist.from_text("Road trip;Intro;Highway")
print(mix.tracks)   # ['Intro', 'Highway']
```

A class method receives the class itself as its first parameter, which by convention is called `cls`. `cls(...)` creates an object exactly as `Playlist(...)` does. This is the static factory method from C#, `Playlist.FromText(...)`. `Self` in the annotation means "an object of this class".

## Special methods: `__repr__` and `__eq__`

<Compare>

```csharp title="C#"
class Point(int x, int y)
{
    public override string ToString()
    {
        return $"({x}, {y})";
    }
}

var start = new Point(2, 5);
Console.WriteLine(start);  // (2, 5)
```

```python title="Python"
class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

    def __repr__(self):
        return f"({self.x}, {self.y})"


start = Point(2, 5)
print(start)  # (2, 5)
```

</Compare>

`__init__` is not the only method Python calls on its own. `print(start)` looks for `__repr__`, `a == b` looks for `__eq__`, and `len(x)` looks for `__len__`. These are the **special methods**. In C# their place is taken by `override`, operators, and interfaces such as `IComparable`.

| You write | Python calls | In C# |
| --- | --- | --- |
| `print(p)`, `str(p)`, an f-string | `__str__`, or `__repr__` if there is none | `ToString()` |
| `a == b` | `__eq__` | `Equals`, `operator ==` |
| `a < b`, `sorted(items)` | `__lt__` | `IComparable<T>` |
| `a + b` | `__add__` | `operator +` |
| `len(x)` | `__len__` | `Count` |
| `item in x` | `__contains__` | `Contains` |
| `x[key]` | `__getitem__` | an indexer |

Without `__repr__` an object prints as `<__main__.Point object at 0x7f3a2c1b4d10>`. That makes it the first special method worth writing: it shows up in the console, in the debugger, and when you print a `list` of such objects. You add `__str__` only if you want a separate text for the user.

A class with `__len__` also works in `if cart:` from the first lesson. An object of length zero is falsy.

### Equality

In the first lesson `==` compared the contents of two lists. That is because `list` has an `__eq__`. A class without its own `__eq__` is compared by identity, like a reference type in C#, and `Point(2, 5) == Point(2, 5)` is `False`. To make it compare the values, you add:

```python
    def __eq__(self, other):
        if not isinstance(other, Point):
            return False
        return (self.x, self.y) == (other.x, other.y)
```

`isinstance(other, Point)` is `other is Point` from C#. The two tuples are compared by contents, so one line covers all the fields.

There is also the same catch as with `Equals` without `GetHashCode`. A class with its own `__eq__` stops being hashable: its objects cannot be keys in a `dict` or items in a `set` until you write `__hash__` as well.

In C# a `record` saves you this writing. In Python a dataclass does, and it is the next topic.

## A dataclass in place of a record

<Compare>

```csharp title="C#"
record Point(int X, int Y);

var a = new Point(2, 5);
var b = new Point(2, 5);

Console.WriteLine(a == b);  // True
Console.WriteLine(a);
// Point { X = 2, Y = 5 }
```

```python title="Python"
from dataclasses import dataclass

@dataclass
class Point:
    x: int
    y: int


a = Point(2, 5)
b = Point(2, 5)

print(a == b)  # True
print(a)       # Point(x=2, y=5)
```

</Compare>

`@dataclass` reads the annotated names in the class body and writes `__init__`, `__repr__` and `__eq__` from them, the three methods from the previous topics. Here the lines at the top of the class really are fields, because the decorator turns them into constructor parameters.

The annotation is required: a name without a type does not become a field. The types themselves are still not checked while the program runs, and `Point("a", None)` creates an object without complaint.

In every other way this is an ordinary class, and you can give it methods and properties. Here is what you will use most often:

```python
from dataclasses import dataclass, field, replace

@dataclass
class Playlist:
    name: str
    tracks: list[str] = field(default_factory=list)
    public: bool = False


@dataclass(frozen=True)
class Point:
    x: int
    y: int


start = Point(2, 5)
start.x = 10                    # FrozenInstanceError
moved = replace(start, x=10)    # Point(x=10, y=5)
```

- **A default value** goes after the type: `public: bool = False`. Fields with a default come after the ones without, like optional parameters.
- **A mutable default value** is given with `field(default_factory=list)`. `default_factory` is a function the dataclass calls for every new object, so every playlist gets its own list. If you write `tracks: list[str] = []`, the dataclass refuses as soon as the class is defined. It is the trap from the first lesson, caught in time for once.
- **`frozen=True`** makes the object immutable: assigning to a field raises a `FrozenInstanceError`. A frozen dataclass is hashable too, so it can be a key in a `dict`.
- **`replace(start, x=10)`** returns a copy with one field changed. In C# this is `start with { X = 10 }`.
- **`order=True`** adds `<`, `>` and the other comparisons. The fields are compared in the order they are written, as with a tuple.

`x=10` is an argument passed by name. You can call the constructor that way too: `Point(x=2, y=5)`, which in C# is `new Point(X: 2, Y: 5)`.

The difference from C# is in what you get without asking for it. A `record` is immutable, and a dataclass is not. When you need a `record`, write `@dataclass(frozen=True)`.

## Inheritance

<Compare>

```csharp title="C#"
class Parcel(double kg)
{
    public double Kg = kg;

    public virtual double Price()
    {
        return Kg * 2;
    }
}

class Express(double kg, double fee)
    : Parcel(kg)
{
    public override double Price()
    {
        return base.Price() + fee;
    }
}
```

```python title="Python"
class Parcel:
    def __init__(self, kg):
        self.kg = kg

    def price(self):
        return self.kg * 2


class Express(Parcel):
    def __init__(self, kg, fee):
        super().__init__(kg)
        self.fee = fee

    def price(self):
        base = super().price()
        return base + self.fee
```

</Compare>

The base class goes in parentheses after the name, and `super()` is `base`. Three rules differ from C#:

- **The base `__init__` is not called for you.** Once the subclass has its own `__init__`, it has to call `super().__init__(...)`. Leave that out and `self.kg` is never created, and the error comes later, from the first method that reads it. A subclass without its own `__init__` uses the one from the base class.
- **Every method is `virtual`.** A method with the same name in the subclass replaces the base one, with no `virtual` and no `override`. Nobody checks that you really are replacing something, so `def pirce(self)` is a new method, not an error. Since Python 3.12 you can put `@override` from `typing` above the method, and the type checker complains if the base class has no such method.
- **`abstract` is not a keyword.** An abstract class is made with the `abc` module:

```python
from abc import ABC, abstractmethod

class Shipment(ABC):
    @abstractmethod
    def price(self) -> float: ...


Shipment()   # TypeError: Can't instantiate abstract class Shipment
```

The three dots are valid Python and stand in for an empty body. The word `pass` does the same job. A class that inherits from `Shipment` can be created only once it has its own `price`.

`isinstance(box, Parcel)` is `box is Parcel`, and it is true for subclasses too. Python also allows several base classes at once, `class C(A, B)`, but you will meet that in libraries more often than you will write it.

Inheritance is written less often in Python than in C#. Much of it in C# exists so that one method can accept different objects. Here you do not need a common base class for that, and the last topic shows why.

## Duck typing and `Protocol`

<Compare>

```csharp title="C#"
interface INotifier
{
    void Send(string text);
}

class EmailNotifier : INotifier
{
    public void Send(string text)
        => Console.WriteLine(text);
}

void Alert(INotifier notifier)
{
    notifier.Send("Disk is full");
}

Alert(new EmailNotifier());
```

```python title="Python"
class EmailNotifier:
    def send(self, text):
        print(text)


def alert(notifier):
    notifier.send("Disk is full")


alert(EmailNotifier())
```

</Compare>

The Python code has no interface, and it works all the same. `alert` does not ask what type `notifier` is. It calls `send`, and if the object has such a method, all is well. This is called **duck typing**, after the saying: if it walks like a duck and quacks like a duck, it is a duck. What matters is what the object can do, not what it inherits from.

You are already using it. `len()` works with anything that has `__len__`, and `for` walks over anything that can be walked over.

The price is that `def alert(notifier)` says nothing, either to the person reading the code or to the editor. A wrong object is found only when the program reaches `send` and raises an `AttributeError`. That is what `Protocol` is for: an interface meant for the type checker.

```python
from typing import Protocol

class Notifier(Protocol):
    def send(self, text: str) -> None: ...


class EmailNotifier:
    def send(self, text: str) -> None:
        print(f"mail: {text}")


class SmsNotifier:
    def send(self, text: str) -> None:
        print(f"sms: {text}")


def alert(notifier: Notifier) -> None:
    notifier.send("Disk is full")


alert(EmailNotifier())
alert(SmsNotifier())
```

Neither `EmailNotifier` nor `SmsNotifier` mentions `Notifier`. A class satisfies a protocol when it has the protocol's methods with the same parameters. It does not have to inherit from it, or even know that it exists. In C# the class has to name its interface. If you have written TypeScript, the rule is familiar: interfaces work the same way there.

Two conveniences follow from this. With a protocol you can describe a class that is not yours, from a third-party library for example, without touching it. And in tests the fake `Notifier` is a three-line class with one method, with no mocking library.

The checking is still the type checker's job. While the program runs, `alert(42)` still reaches `send` and still raises an `AttributeError`. The C# habit of asking `obj is INotifier` does not work either: `isinstance(obj, Notifier)` raises a `TypeError`, unless the protocol is marked with `@runtime_checkable`.

A `Protocol` is enough when all you need is "an object with these methods". You choose an abstract class with `ABC` when the subclasses should also get shared code.

```python title="cart.py"
        self._lines: list[tuple[str, float, int]] = []

        self._lines.append((name, price, qty))

    @property
    def total(self) -> float:
        total = 0.0
        for _, price, qty in self._lines:
            total += price * qty
        return total

    def __len__(self) -> int:
        return len(self._lines)


cart = Cart()
cart.add("pen", 1.50, 2)
cart.add("mug", 8.00)

print(f"{len(cart)} items, {cart.total:.2f}")
```

The list is created in `__init__`, so every cart has its own. `total` is a property because it is a value you read, not an action. The name `_` in the loop is for a value you do not need, like a discard in C#.

</details>

```python title="version.py"
from dataclasses import dataclass
from typing import Self


@dataclass(frozen=True, order=True)
class Version:
    major: int
    minor: int = 0
    patch: int = 0

    @classmethod
    def parse(cls, text: str) -> Self:
        major, minor, patch = text.split(".")
        return cls(int(major), int(minor), int(patch))

    def __str__(self) -> str:
        return f"{self.major}.{self.minor}.{self.patch}"


installed = Version.parse("3.12.1")
required = Version(3, 12)

print(installed)
print(installed >= required)
```

### Discounts

A shop applies its discounts one after another. Every discount is an object with a method `apply(amount)` that receives a price and returns the new one.

```python title="discounts.py"
from typing import Protocol


class Discount(Protocol):
    def apply(self, amount: float) -> float: ...


class Percent:
    def __init__(self, percent: float) -> None:
        self.percent = percent

    def apply(self, amount: float) -> float:
        return amount * (1 - self.percent / 100)


class Capped(Percent):
    def __init__(self, percent: float, limit: float) -> None:
        super().__init__(percent)
        self.limit = limit

    def apply(self, amount: float) -> float:
        return max(super().apply(amount), amount - self.limit)


def final_price(amount: float, discounts: list[Discount]) -> float:
    for discount in discounts:
        amount = discount.apply(amount)
    return amount


price = final_price(80, [Percent(25), Capped(50, 10)])
print(f"{price:.2f}")
```

`Capped` takes the percentage and the arithmetic from `Percent` and adds only the limit. `final_price` knows about neither of the two classes, it only calls `apply`. That is why it also works with the rule from the check, which was written somewhere else.

## Summary

- An object is created without `new`. `__init__` does the constructor's job, and `self` is written in every method.
- There is no `private`. The underscore is a convention, and `@property` turns a method into a property when you need logic.
- A name in the class body is a **class attribute**, shared by all objects. The object's own data is created in `__init__`.
- Special methods such as `__repr__`, `__eq__` and `__len__` connect a class to `print`, `==` and `len()`.
- **`@dataclass`** writes `__init__`, `__repr__` and `__eq__` for you. With `frozen=True` it is the closest thing to a `record`.
- With inheritance the base `__init__` is called explicitly through `super()`, and every method can be replaced.
- With **duck typing** what matters is which methods an object has. A **`Protocol`** describes those methods for the type checker, without the classes inheriting from it.
