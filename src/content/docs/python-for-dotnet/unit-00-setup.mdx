## Инсталация на Python

**Python е interpreter: няма отделни SDK и runtime и няма build стъпка.**

В .NET инсталираш SDK (CLI + компилатор + runtime). В Python инсталираш interpreter — една програма (`python.exe` / `python3`), която компилира кода до bytecode в момента на изпълнение и веднага го изпълнява. Няколко версии могат да съществуват една до друга (както няколко SDK-та), а коя се стартира зависи от `PATH` и — на Windows — от launcher-а `py`.

dotnet --list-sdks   # всички SDK-та
dotnet --info

<MentalModelShift>
- **Няма build артефакт.** .NET компилира до IL веднъж, runtime-ът JIT-ва. Python компилира всеки модул до bytecode при първото зареждане (кешира го в `__pycache__/*.pyc`) и го изпълнява веднага. Няма `bin/Release`, което да deploy-ваш — deploy-ваш изходния код.

</MentalModelShift>

## Проверка: interpreter и PATH

**Първият въпрос при всеки Python проблем е: „кой interpreter всъщност се изпълни?“**

`dotnet` е един muxer, който сам намира правилното SDK. В Python няма такъв слой (освен `py` на Windows) — стартира се първият `python` по `PATH`. Истината винаги казва `sys.executable`:

python -c "import sys; print(sys.executable)"
```

</TabItem>
<TabItem label="macOS">

python3 --version
which -a python3              # всички python3 в PATH, по ред
python3 -c "import sys; print(sys.executable)"
```

</TabItem>
<TabItem label="Linux">

```bash
python3 --version
which -a python3

```

</TabItem>

В този модул пишем `python` в командите; замени с `py` или `python3` според системата си. След секция 07 ще работиш винаги в `.venv`, където `python` е еднозначно — на всяка ОС.

<PitfallCallout title="Предвиди резултата">
На Windows `python --version` печата 3.12, а `py --version` — 3.14. Натискаш *Run* във VS Code. Коя версия изпълнява `main.py`?

**Нито една от двете команди не решава.** VS Code използва **избрания в status bar interpreter** (секция 03), а не терминалния `PATH`. Три различни отговора на един и същ въпрос — затова `sys.executable` е първото нещо, което печаташ при съмнение.
</PitfallCallout>

## VS Code и Python extension

**Същият редактор, друго разширение: `ms-python.python` носи IntelliSense (Pylance), debugger (debugpy) и избора на interpreter.**

1. Инсталирай [VS Code](https://code.visualstudio.com/) (ако липсва) и extension-а **Python** от Microsoft (`ms-python.python`). То автоматично добавя **Pylance** и **Python Debugger**.
2. Създай празна папка `hello-python` и я отвори: `code hello-python`.
3. **Избери interpreter**: <kbd>Ctrl</kbd>+<kbd>Shift</kbd>+<kbd>P</kbd> → *Python: Select Interpreter* → избери инсталацията от предишната секция (по-късно тук ще избираш `.venv`). Избраният interpreter се вижда **долу вдясно в status bar** — това е еквивалентът на „target framework + SDK“ в едно.
4. По избор: `"editor.formatOnSave": true` и extension-ът **Ruff** (linter + formatter). Ще ги систематизираме в Unit 08.

<MentalModelShift>
- **Няма project файл.** C# Dev Kit работи около `.sln`/`.csproj`. Python extension-ът работи около **папка + избран interpreter**. „Проектът“ е директорията.
- Изборът на interpreter се пази в workspace настройките на VS Code (`.vscode/settings.json`, `python.defaultInterpreterPath`) — незадължително, но полезно в екип.
- **Pylance ≈ Roslyn в редактора**, но само в редактора. Той подчертава грешки статично; нищо не те спира да стартираш кода въпреки тях.
</MentalModelShift>

## Първият скрипт: main.py

**Един файл, без проект, без `Main` — модулът се изпълнява отгоре надолу.**

<CodeComparison csharpFile="Program.cs" pythonFile="main.py">
<Fragment slot="csharp">

```csharp frame="none"
// dotnet new console (top-level statements)
string Greet(string name) => $"Hello, {name}!";

Console.WriteLine(Greet("Curious Otter"));
```

</Fragment>
<Fragment slot="python">

```python frame="none"
def greet(name: str) -> str:
    return f"Hello, {name}!"


if __name__ == "__main__":
    print(greet("Curious Otter"))
```

</Fragment>
</CodeComparison>

<MentalModelShift>
- **`if __name__ == "__main__":` е конвенцията за entry point**, не изискване на езика. Блокът под него се изпълнява само когато файлът е стартиран директно; когато друг модул го `import`-не, `__name__` е името на модула и блокът се пропуска (Unit 02). Без guard-а скриптът също работи — но всеки `import` би отпечатал поздрава.
- **Блоковете са с отстъп, не със скоби.** `:` отваря блок; стандартът (PEP 8) е 4 интервала. Два празни реда между top-level дефиниции — formatter-ите го правят вместо теб.
- **Type hints не се проверяват при изпълнение.** `name: str` и `-> str` са метаданни за редактора и за Pyright (Unit 08). `greet(42)` се изпълнява и връща `"Hello, 42!"`.
- `f"Hello, {name}!"` ≈ `$"Hello, {name}!"`. `print` добавя нов ред, като `Console.WriteLine`.
- Конвенции: `snake_case` за функции и променливи, `PascalCase` само за класове.
</MentalModelShift>

## Изпълнение и четене на грешки

**Грешките идват при изпълнение, не при компилация — и traceback-ът се чете отдолу нагоре.**

Между теб и стартирания код няма компилатор. Typo в име е `NameError` в момента, в който редът се изпълни — а ако редът е в клон, който не се изпълнява, грешката изобщо не се появява. Pylance хваща много от тези случаи в редактора, но не е гаранция като C# компилатора. Когато нещо гръмне, Python печата traceback:

```text
Traceback (most recent call last):
  File "main.py", line 6, in <module>
    print(great("Curious Otter"))
          ^^^^^
NameError: name 'great' is not defined. Did you mean: 'greet'?
```

<MentalModelShift>
- **Обратен ред спрямо .NET.** C# stack trace започва с най-скорошното повикване. Python казва „most recent call last“: **последният ред е какво се е случило, редът над него — къде**. Чети отдолу нагоре.
- **Exit code 1** при неуловено изключение — същото като unhandled exception в конзолно .NET приложение, удобно за скриптове и CI.
- Грешки от първия ден: `NameError` (typo или недефинирано име), `IndentationError` / `TabError` (грешен или смесен отстъп), `SyntaxError: expected ':'`, `ModuleNotFoundError` (пакетът не е инсталиран в *този* interpreter — секция 07) и `TypeError: can only concatenate str (not "int") to str` — Python не вика `ToString()` вместо теб.
</MentalModelShift>

## Debugging във VS Code

**Същите клавиши, друг debugger (debugpy) — плюс вграден `breakpoint()`.**

1. Кликни вляво от номера на реда `return f"Hello, {name}!"` (или <kbd>F9</kbd>) — червена точка.
2. <kbd>F5</kbd> → при първо стартиране избери **Python Debugger: Python File**. Изпълнението спира на breakpoint-а.
3. Панелите са познатите: **Variables** (локалната `name`), **Watch**, **Call Stack** и **Debug Console** — в него изпълняваш Python изрази в паузирания контекст, като Immediate Window.
4. <kbd>F10</kbd> Step Over, <kbd>F11</kbd> Step Into, <kbd>Shift</kbd>+<kbd>F11</kbd> Step Out, <kbd>F5</kbd> Continue — както във Visual Studio.
5. `breakpoint()` в кода е програмен breakpoint — аналог на `Debugger.Break()`. Под debugger спира там; без debugger отваря вградения `pdb` в терминала (`c` продължава, `q` излиза).
6. `launch.json` не е задължителен — конфигурацията *Python File* е вградена. Нужен е само когато подаваш аргументи или environment variables (*Run and Debug → create a launch.json file*).

| Visual Studio / C# | VS Code / Python | Бележка |
| --- | --- | --- |
| <kbd>F5</kbd>, <kbd>F9</kbd>, <kbd>F10</kbd>, <kbd>F11</kbd> | същите | VS Code keymap по подразбиране |
| Immediate Window | Debug Console | изпълнява реален Python в текущия frame |
| `Debugger.Break()` | `breakpoint()` | вграден в езика от Python 3.7 |
| Edit & Continue / Hot Reload | — | рестартираш; скриптовете стартират за милисекунди |

<MentalModelShift>
Debug Console изпълнява истински Python в паузирания frame: можеш да извикаш `greet("x")`, да видиш `type(name)` или `dir(name)`. В динамичен език това е първокласен начин да изследваш API — не само да ловиш bug-ове.
</MentalModelShift>

## Virtual environment (.venv)

**`pip install` инсталира в активния interpreter. Без `.venv` „активният interpreter“ е цялата машина.**

NuGet възстановява пакетите в глобален кеш (`~/.nuget/packages`), но всеки проект ги *референцира* през `.csproj` — два проекта могат да ползват различни версии без конфликт. `pip` инсталира в `site-packages` на interpreter-а, който го е извикал: един общ пул за всички проекти на тази версия. `.venv` е изолирано копие (или link) на interpreter-а със собствен `site-packages` — по една среда на проект.

<Tabs syncKey="os">
<TabItem label="Windows">

```powershell
cd hello-python
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -c "import sys; print(sys.executable)"   # ...\hello-python\.venv\Scripts\python.exe
python -m pip --version                          # pip ... from ...\.venv\...
```

Ако PowerShell откаже да изпълни `Activate.ps1` (execution policy), разреши еднократно подписаните локални скриптове за своя потребител: `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`. В `cmd` активирането е `.venv\Scripts\activate.bat`.

</TabItem>
<TabItem label="macOS">

```bash
cd hello-python
python3 -m venv .venv
source .venv/bin/activate
python -c "import sys; print(sys.executable)"   # .../hello-python/.venv/bin/python
python -m pip --version
```

</TabItem>
<TabItem label="Linux">

```bash
cd hello-python
python3 -m venv .venv
source .venv/bin/activate
python -c "import sys; print(sys.executable)"   # .../hello-python/.venv/bin/python
python -m pip --version
```

</TabItem>
</Tabs>

След активиране prompt-ът започва с `(.venv)` и вътре `python` е еднозначно — край на танца `py` / `python3`. `deactivate` излиза от средата.

**VS Code** разпознава новата `.venv` и предлага да я избере; ако не — *Python: Select Interpreter* → `./.venv/...`. Новите вградени терминали се отварят с активирана среда. Алтернатива: *Python: Create Environment* → *Venv* създава и избира средата с една команда.

Първата зависимост и проверката, че е отишла на правилното място:

```powershell
python -m pip install requests
python -m pip list
```

<MentalModelShift>
- **NuGet: глобален кеш + per-project граф. pip: per-environment инсталация.** `.venv` е това, което прави „per-project“ вярно и за Python.
- **Средата е за еднократна употреба.** `dotnet restore` пресъздава `obj/` от `.csproj`; `python -m venv .venv` + `pip install -r requirements.txt` пресъздава средата от списъка. Затова `.venv/` отива в `.gitignore`, както `bin/` и `obj/`. Съвременният еквивалент на `.csproj` е `pyproject.toml` — Unit 08.
- **`python -m pip`, не `pip`.** Така pip-ът е гарантирано на *този* interpreter; голото `pip` в `PATH` може да е на друга инсталация.
- **Linux и PEP 668.** Системният Python отказва `pip install` именно за да не счупиш ОС-а — `.venv` е отговорът, не `--break-system-packages`.
</MentalModelShift>

<PitfallCallout>
Терминал, отворен **преди** да избереш `.venv`, не е активиран — `pip install` в него отива в глобалния interpreter, а после `import` във VS Code дава `ModuleNotFoundError`. Затвори го и отвори нов, или активирай ръчно. Проверка: `python -m pip --version` трябва да покаже път вътре в `.venv`.
</PitfallCallout>

## .NET ↔ Python: карта на инструментите

**Аналогии за ориентация — не еквиваленти.**

| .NET | Python | Бележка |
| --- | --- | --- |
| `dotnet --version` | `python --version`, `py -0p` | в .NET версията е на SDK, в Python — на interpreter-а |
| SDK + runtime | interpreter | един компонент: компилира до bytecode и изпълнява |
| `dotnet new console` | `mkdir` + `main.py` | няма шаблон, няма project файл |
| `Program.cs` / `Main` | `main.py` / `if __name__ == "__main__":` | конвенция, не изискване |
| `dotnet run` | `python main.py` | няма build стъпка; bytecode кеш в `__pycache__` |
| `dotnet build` | — | няма отделен артефакт за deploy |
| `.csproj` + NuGet | `pyproject.toml` + PyPI (`pip` / `uv`) | концептуален аналог, различен модел на инсталиране |
| `global.json` | избран interpreter / `.venv` | фиксира версията за проекта |
| `bin/`, `obj/` | `.venv/`, `__pycache__/` | не се commit-ват |
| `Debugger.Break()` | `breakpoint()` | вграден в езика |
| Immediate Window | Debug Console, REPL (`python`) | REPL-ът е ежедневен инструмент в Python |

## TL;DR

**Шест съответствия, които да запомниш от този модул.**

- **Interpreter вместо SDK + runtime.** `python --version` и `sys.executable` са първите команди при съмнение.
- **Папка + `main.py` вместо проект.** `if __name__ == "__main__":` играе ролята на `Main`, но е конвенция.
- **`python main.py` вместо `dotnet run`.** Няма build стъпка; bytecode кешът е в `__pycache__`.
- **Traceback се чете отдолу нагоре.** Последният ред — какво; редът над него — къде.
- **Винаги `.venv`, винаги `python -m pip`.** `.venv/` в `.gitignore`, както `bin/` и `obj/`.
- **Същите debug клавиши.** `breakpoint()` ≈ `Debugger.Break()`, Debug Console ≈ Immediate Window.
