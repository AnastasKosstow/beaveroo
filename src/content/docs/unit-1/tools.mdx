Един ключов аспект на AI Agents е способността им да предприемат **actions**. Както видяхме, това се случва чрез използването на **Tools**.

В тази секция ще научим какво са Tools, как да ги проектираме ефективно и как да ги интегрираме в своя Agent чрез System Message.

Като дадеш на своя Agent правилните Tools — и ясно опишеш как работят те — можеш драстично да увеличиш това, което твоят AI може да постигне. Да се потопим!

## Какво са AI Tools?

**Tool е функция, предоставена на LLM**. Тази функция трябва да изпълнява **ясна цел**.

Ето някои често използвани tools в AI agents:

| Tool | Описание |
|------|----------|
| Web Search | Позволява на agent-а да извлича актуална информация от интернет. |
| Image Generation | Създава изображения по текстови описания. |
| Retrieval | Извлича информация от външен източник. |
| API Interface | Взаимодейства с външен API (GitHub, YouTube, Spotify и т.н.). |

Това са само примери — всъщност можеш да създадеш tool за всякакъв случай!

Добрият tool трябва да е нещо, което **допълва силата на LLM**.

Например, ако трябва да извършваш аритметика, предоставянето на **calculator tool** на твоя LLM ще даде по-добри резултати, отколкото разчитането на вродените възможности на модела.

Освен това **LLMs предсказват допълването на prompt въз основа на данните, с които са обучени**, което означава, че вътрешните им знания включват само събития отпреди обучението им. Следователно, ако твоят agent има нужда от актуални данни, трябва да му ги предоставиш чрез някакъв tool.

Например, ако попиташ LLM директно (без search tool) какво е времето днес, LLM вероятно ще халюцинира случайна прогноза.

<img src="https://huggingface.co/datasets/agents-course/course-images/resolve/main/en/unit1/weather.jpg" alt="Времето"/>

- Един Tool трябва да съдържа:

  - **Текстово описание на това, което прави функцията**.
  - *Callable* (нещо, което изпълнява action).
  - *Аргументи* с типове.
  - (По избор) Изходи с типове.

## Как работят tools?

LLMs, както видяхме, могат само да получават текстов вход и да генерират текстов изход. Те нямат начин сами да извикват tools. Когато говорим за предоставяне на tools на Agent, имаме предвид да научим LLM за съществуването на тези tools и да го инструктираме да генерира текстови извиквания, когато е необходимо.

Например, ако предоставим tool за проверка на времето на дадено място от интернет и после попитаме LLM за времето в Париж, LLM ще разпознае, че това е възможност да използва „weather“ tool-а. Вместо сам да извлича данните за времето, LLM ще генерира текст, който представлява извикване на tool, например `call weather_tool('Paris')`.

**Agent-ът** след това чете този отговор, идентифицира, че е необходимо извикване на tool, изпълнява tool-а от името на LLM и извлича реалните данни за времето.

Стъпките по извикването на Tool обикновено не се показват на потребителя: Agent-ът ги добавя като ново съобщение, преди да подаде обновения разговор отново на LLM. LLM след това обработва този допълнителен контекст и генерира естествено звучащ отговор за потребителя. От гледна точка на потребителя изглежда сякаш LLM директно е взаимодействал с tool-а, но в действителност Agent-ът е този, който е извършил целия процес на изпълнение във фонов режим.

Ще говорим много повече за този процес в следващите сесии.

## Как даваме tools на LLM?

Пълният отговор може да изглежда обезкуражаващ, но по същество използваме system prompt-а, за да предоставим на модела текстови описания на наличните tools:

<img src="https://huggingface.co/datasets/agents-course/course-images/resolve/main/en/unit1/Agent_system_prompt.png" alt="System prompt за tools"/>

За да работи това, трябва да сме много прецизни и точни относно:

1. **Какво прави tool-ът**
2. **Какви точно входове очаква**

Това е причината описанията на tools обикновено да се предоставят чрез изразителни, но прецизни структури, като езици за програмиране или JSON. Не е _задължително_ да се прави така — всеки прецизен и последователен формат би работил.

Ако това ти се струва твърде теоретично, да го разберем чрез конкретен пример.

Ще реализираме опростен **calculator** tool, който просто умножава две цели числа. Ето как може да изглежда нашата C# реализация:

```csharp
/// <summary>Multiply two integers.</summary>
int Calculator(int a, int b)
{
    return a * b;
}
```

И така, нашият tool се казва `Calculator`, той **умножава две цели числа** и изисква следните входове:

- **`a`** (*int*): цяло число.
- **`b`** (*int*): цяло число.

Изходът на tool-а е друго цяло число, което можем да опишем така:
- (*int*): произведението на `a` и `b`.

Всички тези детайли са важни. Да ги съберем в текстов низ, който описва нашия tool така, че LLM да го разбере.

```text
Tool Name: calculator, Description: Multiply two integers., Arguments: a: int, b: int, Outputs: int
```

> **Напомняне:** Това текстово описание е *това, което искаме LLM да знае за tool-а*.

Когато подадем предишния низ като част от входа към LLM, моделът ще го разпознае като tool и ще знае какво трябва да подаде като вход и какво да очаква като изход.

Ако искаме да предоставим допълнителни tools, трябва да сме последователни и винаги да използваме същия формат. Този процес може да е крехък и неволно да пропуснем някои детайли.

Има ли по-добър начин?

### Автоматично форматиране на секциите за Tools

Нашият tool е написан на C# и реализацията вече предоставя всичко, от което се нуждаем:

- Описателно име на това, което прави: `Calculator`
- По-дълго описание, предоставено от коментара към функцията: `Multiply two integers.`
- Входовете и техните типове: функцията ясно очаква два `int`.
- Типа на изхода.

Има причина хората да използват езици за програмиране: те са изразителни, кратки и прецизни.

Бихме могли да предоставим C# изходния код като _спецификация_ на tool-а за LLM, но начинът, по който tool-ът е реализиран, няма значение. Единственото, което има значение, са името му, какво прави, входовете, които очаква, и изходът, който предоставя.

Ще се възползваме от възможностите за **reflection** в .NET, за да използваме информацията от самия код и автоматично да изградим описание на tool-а. Всичко, което ни трябва, е реализацията на tool-а да използва типове за параметрите (в C# те са задължителни — това е предимство спрямо Python), описание и смислени имена на функциите. Ще напишем малко код, който да извлича нужните части.

Има една важна разлика спрямо Python: XML коментарите (`/// <summary>`) **не са достъпни по време на изпълнение**. Затова в .NET описанието се поставя в атрибут — `[Description]` от `System.ComponentModel`. Точно този атрибут използват и реалните .NET библиотеки за AI (например `Microsoft.Extensions.AI` и Semantic Kernel).

След като приключим, ще ни трябва само атрибутът `[Description]` и едно извикване на `Tool.FromMethod`, за да обявим, че функцията `Calculator` е tool:

```csharp
using System.ComponentModel;

public static class MathTools
{
    [Description("Multiply two integers.")]
    public static int Calculator(int a, int b) => a * b;
}
```

```csharp
var calculatorTool = Tool.FromMethod(MathTools.Calculator);
Console.WriteLine(calculatorTool.ToString());
```

Обърни внимание на атрибута `[Description]` над дефиницията на функцията — той играе ролята на Python decorator-а `@tool` в комбинация с docstring-а.

С реализацията, която ще видим след малко, ще можем автоматично да извлечем следния текст от изходния код чрез метода `ToString()`, предоставен от класа `Tool`:

```text
Tool Name: calculator, Description: Multiply two integers., Arguments: a: int, b: int, Outputs: int
```

Както виждаш, това е същото нещо, което написахме ръчно преди!

### Генерична реализация на Tool

Създаваме генеричен клас `Tool`, който можем да използваме повторно винаги когато имаме нужда от tool.

> **Уточнение:** Тази примерна реализация е измислена, но много прилича на реалните реализации в повечето библиотеки.

```csharp
/// <summary>
/// Клас, представящ преизползваемо парче код (Tool).
/// </summary>
public class Tool
{
    /// <summary>Име на tool-а.</summary>
    public string Name { get; }

    /// <summary>Текстово описание на това, което прави tool-ът.</summary>
    public string Description { get; }

    /// <summary>Функцията, която този tool обвива.</summary>
    public Delegate Func { get; }

    /// <summary>Списък с аргументи (име и тип).</summary>
    public IReadOnlyList<(string Name, string Type)> Arguments { get; }

    /// <summary>Типът, който връща обвитата функция.</summary>
    public string Outputs { get; }

    public Tool(
        string name,
        string description,
        Delegate func,
        IReadOnlyList<(string Name, string Type)> arguments,
        string outputs)
    {
        Name = name;
        Description = description;
        Func = func;
        Arguments = arguments;
        Outputs = outputs;
    }

    /// <summary>
    /// Връща текстово представяне на tool-а,
    /// включващо името, описанието, аргументите и изхода му.
    /// </summary>
    public override string ToString()
    {
        string args = string.Join(", ", Arguments.Select(arg => $"{arg.Name}: {arg.Type}"));

        return $"Tool Name: {Name}," +
               $" Description: {Description}," +
               $" Arguments: {args}," +
               $" Outputs: {Outputs}";
    }

    /// <summary>
    /// Извиква обвитата функция (callable) с подадените аргументи.
    /// </summary>
    public object? Invoke(params object?[] args) => Func.DynamicInvoke(args);
}
```

Може да изглежда сложно, но ако го разгледаме бавно, ще видим какво прави. Дефинираме клас **`Tool`**, който включва:

- **`Name`** (*string*): името на tool-а.
- **`Description`** (*string*): кратко описание на това, което прави tool-ът.
- **`Func`** (*Delegate*): функцията, която tool-ът изпълнява.
- **`Arguments`** (*списък*): очакваните входни параметри.
- **`Outputs`** (*string*): очаквания изход на tool-а.
- **`Invoke()`**: извиква функцията, когато tool-ът бъде използван (аналог на `__call__()` в Python).
- **`ToString()`**: преобразува атрибутите на tool-а в текстово представяне.

Бихме могли да създадем Tool с този клас, използвайки код като следния:

```csharp
var calculatorTool = new Tool(
    "calculator",                   // име
    "Multiply two integers.",       // описание
    MathTools.Calculator,           // функцията, която ще се извиква
    [("a", "int"), ("b", "int")],   // входове (имена и типове)
    "int"                           // изход
);
```

Но можем да използваме и **reflection** в .NET (`System.Reflection`), за да извлечем цялата информация вместо нас! Това прави статичният метод `Tool.FromMethod` — аналогът на decorator-а `@tool`.

> Ако ти е интересно, можеш да разгънеш следващата секция, за да видиш реализацията.

<details>
<summary>Кодът на Tool.FromMethod</summary>

```csharp
using System.ComponentModel;
using System.Reflection;
using System.Text.Json;

public class Tool
{
    // ... свойствата, конструкторът, ToString() и Invoke() отгоре ...

    /// <summary>
    /// Създава инстанция на Tool от подадената функция (аналог на decorator-а @tool).
    /// </summary>
    public static Tool FromMethod(Delegate func)
    {
        // Вземаме метаданните на метода
        MethodInfo method = func.Method;

        // Извличаме двойки (име на параметър, тип) за входовете
        var arguments = method.GetParameters()
            .Select(parameter => (Name: parameter.Name!, Type: TypeName(parameter.ParameterType)))
            .ToList();

        // Определяме типа на връщаната стойност
        string outputs = method.ReturnType == typeof(void)
            ? "No return annotation"
            : TypeName(method.ReturnType);

        // Използваме атрибута [Description] като описание (с текст по подразбиране, ако липсва)
        string description = method.GetCustomAttribute<DescriptionAttribute>()?.Description
            ?? "No description provided.";

        // Името на метода става име на Tool (в snake_case, както е прието за tools)
        string name = JsonNamingPolicy.SnakeCaseLower.ConvertName(method.Name);

        // Връщаме нова инстанция на Tool
        return new Tool(
            name: name,
            description: description,
            func: func,
            arguments: arguments,
            outputs: outputs
        );
    }

    /// <summary>Превежда .NET имената на типовете (Int32, String...) към C# ключовите думи.</summary>
    private static string TypeName(Type type) => type switch
    {
        _ when type == typeof(int) => "int",
        _ when type == typeof(string) => "string",
        _ when type == typeof(bool) => "bool",
        _ when type == typeof(double) => "double",
        _ => type.Name,
    };
}
```

</details>

За да повторим — с този метод на разположение можем да реализираме нашия tool така:

```csharp
public static class MathTools
{
    [Description("Multiply two integers.")]
    public static int Calculator(int a, int b) => a * b;
}
```

```csharp
var calculatorTool = Tool.FromMethod(MathTools.Calculator);
Console.WriteLine(calculatorTool.ToString());
```

И можем да използваме метода `ToString` на `Tool`, за да извлечем автоматично текст, подходящ за описание на tool-а пред LLM:

```text
Tool Name: calculator, Description: Multiply two integers., Arguments: a: int, b: int, Outputs: int
```

Описанието се **инжектира** в system prompt-а. Ако вземем примера, с който започнахме тази секция, ето как би изглеждал той след заместването на `tools_description`:

:::tip[Как е в реалните .NET библиотеки?]
Библиотеката `Microsoft.Extensions.AI` прави точно това, което направихме ръчно — чрез `AIFunctionFactory` тя чете името, атрибута `[Description]` и параметрите на метода и генерира описание във формат JSON Schema, разбираем за всички съвременни модели с function calling:

```csharp
using Microsoft.Extensions.AI;

AIFunction calculator = AIFunctionFactory.Create(MathTools.Calculator);

Console.WriteLine(calculator.Name);        // Calculator
Console.WriteLine(calculator.Description); // Multiply two integers.
Console.WriteLine(calculator.JsonSchema);  // JSON Schema на параметрите a и b
```

Ще използваме този подход, когато изграждаме [първия си Agent](/unit-1/tutorial/).

### Model Context Protocol (MCP): унифициран интерфейс за tools

Model Context Protocol (MCP) е **отворен протокол**, който стандартизира начина, по който приложенията **предоставят tools на LLMs**.
MCP предоставя:

- Нарастващ списък от готови интеграции, към които твоят LLM може директно да се включи
- Гъвкавост при смяна на доставчици на LLM
- Добри практики за защита на данните в твоята инфраструктура

Това означава, че **всеки framework, който реализира MCP, може да използва tools, дефинирани в рамките на протокола**, което премахва нуждата да се реализира един и същ интерфейс за tools за всеки framework поотделно. В .NET има официален [MCP C# SDK](https://github.com/modelcontextprotocol/csharp-sdk) (NuGet пакетът `ModelContextProtocol`), който се интегрира директно с `Microsoft.Extensions.AI`.

Ако искаш да навлезеш по-дълбоко в MCP, можеш да разгледаш безплатния [MCP Course](https://huggingface.co/learn/mcp-course/) на Hugging Face.

Tools играят ключова роля в разширяването на възможностите на AI agents.

В обобщение, научихме:

- *Какво са Tools*: функции, които дават на LLMs допълнителни възможности, като извършване на изчисления или достъп до външни данни.

- *Как да дефинираме Tool*: като предоставим ясно текстово описание, входове, изходи и callable функция.

- *Защо Tools са съществени*: те позволяват на Agents да преодолеят ограниченията на статичното обучение на модела, да се справят със задачи в реално време и да изпълняват специализирани actions.
