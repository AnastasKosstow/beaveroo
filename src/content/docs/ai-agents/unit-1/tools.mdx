Един ключов аспект на AI Agents е способността им да предприемат действия (**actions**). Както видяхме, това се случва чрез използването на инструменти (**Tools**).

В тази секция ще научим какво са инструменти (Tools), как да ги проектираме ефективно и как да ги интегрираме в своя Agent чрез System Message.

Като дадеш на своя Agent правилните инструменти (Tools) - и ясно опишеш как работят те - можеш драстично да увеличиш това, което твоят AI може да постигне.

## Какво са AI Tools?

**Tool е функция, предоставена на LLM**. Тази функция трябва да изпълнява **ясна цел**.

Ето някои често използвани tools в AI agents:

| Tool | Описание |
|------|----------|
| Web Search | Позволява на agent-а да извлича актуална информация от интернет. |
| Image Generation | Създава изображения по текстови описания. |
| Retrieval | Извлича информация от външен източник. |
| API Interface | Взаимодейства с външен API (GitHub, YouTube, Spotify и т.н.). |

Това са само примери - всъщност можеш да създадеш tool за всякакъв случай!

Добрият tool трябва да е нещо, което **допълва силата на LLM**.

Например, ако трябва да извършваш аритметика, предоставянето на **calculator tool** на твоя LLM ще даде по-добри резултати, отколкото разчитането на вродените възможности на модела.

Освен това **LLMs предсказват допълването на prompt въз основа на данните с които са обучени**, което означава, че вътрешните им знания включват само събития отпреди обучението им. Следователно, ако твоят agent има нужда от актуални данни, трябва да му ги предоставиш чрез някакъв tool.

Например, ако попиташ LLM директно (без search tool) какво е времето днес, LLM вероятно ще халюцинира случайна прогноза.

![Времето](../../../../assets/course/unit1/weather.jpg)

- Един Tool трябва да съдържа:

  - **Текстово описание на това, което прави функцията**.
  - *Callable* (нещо, което изпълнява action).
  - *Аргументи* с типове.
  - (По избор) Изходи с типове.

## Как работят tools?

LLMs, както видяхме, могат само да получават текстов вход и да генерират текстов изход. Те нямат начин сами да извикват tools. Когато говорим за предоставяне на tools на Agent, имаме предвид да научим LLM за съществуването на тези tools и да го инструктираме да генерира текстови извиквания, когато е необходимо.

Например, ако предоставим tool за проверка на времето на дадено място от интернет и после попитаме LLM за времето в Париж, LLM ще разпознае, че това е възможност да използва „weather“ tool-а. Вместо сам да извлича данните за времето, LLM ще генерира текст, който представлява извикване на tool, например `call weather_tool('Paris')`.

**Agent-ът** след това чете този отговор, идентифицира, че е необходимо извикване на tool, изпълнява tool-а от името на LLM и извлича реалните данни за времето.

Стъпките по извикването на Tool обикновено не се показват на потребителя: Agent-ът ги добавя като ново съобщение, преди да подаде обновения разговор отново на LLM. LLM след това обработва този допълнителен контекст и генерира естествено звучащ отговор за потребителя. От гледна точка на потребителя изглежда сякаш LLM директно е взаимодействал с tool-а, но в действителност Agent-ът е този, който е извършил целия процес на изпълнение във фонов режим.

Ще говорим много повече за този процес в следващите сесии.

## Как даваме tools на LLM?

LLM може да чете само текст. Затова „да дадем tool на модела“ означава нещо съвсем просто: **описваме tool-а с текст и слагаме това описание в system prompt-а**.

```text wrap
You are an AI assistant designed to help users efficiently and accurately. Your primary goal is to provide helpful, precise, and clear responses.

You have access to the following tools:
{tools_description}
```

На мястото на `{tools_description}` ще застанат описанията на нашите tools. В тази секция ще видим как да ги напишем: първо на ръка, а после автоматично от C# кода.

### Какво трябва да знае моделът за един tool?

Когато задържиш мишката върху метод във Visual Studio, IntelliSense ти показва името му, параметрите с техните типове, типа на резултата и кратко описание. Тялото на метода не се вижда, но и не ти трябва, за да го извикаш правилно.

Моделът има нужда от точно същата информация:

1. **Име** на tool-а
2. **Описание** на това, което прави
3. **Входове** - имената и типовете на аргументите
4. **Изход** - типът на резултата

Да вземем за пример опростен **calculator** tool, който умножава две цели числа:

```csharp
int Calculator(int a, int b)
{
    return a * b;
}
```

Името е `Calculator`, описанието е „умножава две цели числа“, входовете са `a` и `b` от тип `int`, а изходът е `int`. Записани като текст, те изглеждат така:

```text wrap
Tool Name: Calculator, Description: Multiply two integers., Arguments: a: int, b: int, Outputs: int
```

> **Важно:** Този текст е *всичко, което моделът знае за tool-а*. Той не вижда самия C# код.

Точно този формат не е задължителен. Може да бъде и JSON. Важното е описанието да е прецизно и да е в един и същ формат за всички tools.

Писането на описания на ръка обаче е крехко. Достатъчно е да преименуваш параметър и да забравиш да поправиш текста, и моделът започва да извиква tool-а грешно, без компилаторът да те предупреди.

### Описанието идва от самия код

Погледни пак метода `Calculator`. Името, параметрите с типовете им и типът на резултата вече са записани в него. Липсва само описанието с думи. За него в .NET се използва атрибутът `[Description]`:

```csharp
using System.ComponentModel;

public static class MathTools
{
    [Description("Multiply two integers.")]
    public static int Calculator(int a, int b) => a * b;
}
```

Защо атрибут, а не `///` коментар? Коментарите изчезват при компилация. Атрибутите остават в компилираната програма и могат да бъдат прочетени, докато тя работи. Четенето на информация за собствения код по време на изпълнение се нарича **reflection** и с него можем да вземем и четирите неща автоматично от обекта `MethodInfo`, който описва метода:

| Какво ни трябва | Откъде го взимаме | Резултат в примера |
| --- | --- | --- |
| Име | `method.Name` | `Calculator` |
| Описание | атрибутът `[Description]` | `Multiply two integers.` |
| Входове | `method.GetParameters()` | `a` и `b` от тип `int` |
| Изход | `method.ReturnType` | `int` |

### Класът Tool

Събираме всичко в един малък клас `Tool` (записан като `record`, за да е кратък), който можем да използваме за всеки наш tool. Първите му редове изброяват от какво се състои един tool: четирите неща от описанието и самият метод (`Func`).

> **Уточнение:** Тази реализация е примерна, но много прилича на реалните реализации в повечето библиотеки.

```csharp
using System.ComponentModel;
using System.Reflection;

public record Tool(
    string Name,
    string Description,
    Delegate Func,
    IReadOnlyList<(string Name, string Type)> Arguments,
    string Outputs)
{
    public static Tool FromMethod(Delegate func)
    {
        MethodInfo method = func.Method;

        string name = method.Name;
        string description =
            method.GetCustomAttribute<DescriptionAttribute>()?.Description ?? "";
        var arguments = method.GetParameters()
            .Select(p => (p.Name!, TypeName(p.ParameterType)))
            .ToList();
        string outputs = TypeName(method.ReturnType);

        return new Tool(name, description, func, arguments, outputs);
    }

    public object? Invoke(params object?[] args) => Func.DynamicInvoke(args);

    public override string ToString()
    {
        string arguments = string.Join(
            ", ", Arguments.Select(a => $"{a.Name}: {a.Type}"));

        return $"Tool Name: {Name}, Description: {Description}, " +
               $"Arguments: {arguments}, Outputs: {Outputs}";
    }

    private static string TypeName(Type type) => type.Name switch
    {
        "Int32" => "int",
        "String" => "string",
        "Boolean" => "bool",
        "Double" => "double",
        var other => other,
    };
}
```

Класът прави три неща:

- **`FromMethod`** прочита метода с reflection и създава `Tool` от него.
- **`ToString`** връща описанието като текст. Това е, което ще види моделът.
- **`Invoke`** изпълнява самия метод. Това ще прави Agent-ът, когато моделът поиска tool-а.

Помощният метод `TypeName` само заменя .NET имената `Int32` и `String` с познатите `int` и `string`.

Да го изпробваме:

```csharp
Tool calculator = Tool.FromMethod(MathTools.Calculator);

Console.WriteLine(calculator);
Console.WriteLine(calculator.Invoke(6, 7));
```

```text wrap
Tool Name: Calculator, Description: Multiply two integers., Arguments: a: int, b: int, Outputs: int
42
```

Първо се отпечатва същото описание, което преди малко написахме на ръка. Този път името, аргументите и типовете идват от самия код и няма как да се разминат с него. След него идва `42`: същият обект може и да изпълни tool-а.

Остава да **вмъкнем** описанието в system prompt-а на мястото на `{tools_description}`:

```text wrap
You are an AI assistant designed to help users efficiently and accurately. Your primary goal is to provide helpful, precise, and clear responses.

You have access to the following tools:
Tool Name: Calculator, Description: Multiply two integers., Arguments: a: int, b: int, Outputs: int
```

Това е всичко. Моделът вече знае, че разполага с `Calculator`, какво прави той и какви входове очаква. В секцията [Actions](/ai-agents/unit-1/actions/) ще научим как Agent **извиква** tool-а, който току-що създадохме.

:::tip[Как е в реалните .NET библиотеки?]
Не е нужно да пишеш собствен клас `Tool`. Библиотеката `Microsoft.Extensions.AI` прави същото чрез `AIFunctionFactory`: чете името на метода, атрибута `[Description]` и параметрите му. Разликата е, че описва входовете във формат JSON Schema, който всички съвременни модели с function calling разбират.

```csharp
using Microsoft.Extensions.AI;

AIFunction calculator = AIFunctionFactory.Create(MathTools.Calculator);

Console.WriteLine(calculator.Name);
Console.WriteLine(calculator.Description);
Console.WriteLine(calculator.JsonSchema);
```

```text wrap
Calculator
Multiply two integers.
{"type":"object","properties":{"a":{"type":"integer"},"b":{"type":"integer"}},"required":["a","b"]}
```

Ще използваме този подход, когато изграждаме [първия си Agent](/ai-agents/unit-1/tutorial/).
:::

### Model Context Protocol (MCP): унифициран интерфейс за tools

Нашият `Tool` работи само в нашата програма. Всяка библиотека за Agents има свой подобен клас, така че един и същ tool трябва да се описва наново за всяка от тях.

Model Context Protocol (MCP) е **отворен протокол**, който стандартизира начина, по който приложенията **предоставят tools на LLMs**. Tool-ът се реализира веднъж, в отделна програма, наречена MCP server, и **всеки framework, който поддържа MCP, може да го използва**.

MCP предоставя:

- Нарастващ списък от готови интеграции, към които твоят LLM може директно да се включи
- Гъвкавост при смяна на доставчици на LLM
- Добри практики за защита на данните в твоята инфраструктура

В .NET има официален [MCP C# SDK](https://github.com/modelcontextprotocol/csharp-sdk) (NuGet пакетът `ModelContextProtocol`), който се интегрира директно с `Microsoft.Extensions.AI`. Ако искаш да навлезеш по-дълбоко в MCP, разгледай безплатния [MCP Course](https://huggingface.co/learn/mcp-course/) на Hugging Face.

Tools играят ключова роля в разширяването на възможностите на AI agents.

В обобщение, научихме:

- *Какво са Tools*: функции, които дават на LLMs допълнителни възможности, като извършване на изчисления или достъп до външни данни.

- *Как да дефинираме Tool*: като предоставим ясно текстово описание, входове, изходи и callable функция.

- *Защо Tools са съществени*: те позволяват на Agents да преодолеят ограниченията на статичното обучение на модела, да се справят със задачи в реално време и да изпълняват специализирани actions.
